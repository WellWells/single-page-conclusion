CLAUDE.md ／ AGENTS.md

每一行都會被讀一遍，
所以每一行都要值得

CLAUDE.md 不是說明文件，而是一份會被塞進每一輪對話的常駐指令。寫得好，代理可以連續跑上幾個小時而不必每五分鐘回頭盯著；寫得爛，它只是持續消耗上下文的雜訊。以下 12 條規則，來自實際被代理犯過的錯。

約 180 行

一份健康的 CLAUDE.md：只放代理反覆問、反覆做錯的事。

500 行

實務上的軟性天花板。超過就該往下拆成巢狀檔案或技能。

超出之後

上下文愈長，模型遵循指令的穩定度愈低，規則反而互相稀釋。

四個核心結論

  • 01

    這份檔案的本質是失敗日誌，不是規格書。每一行都應該對應到代理至少犯過一次的錯。

  • 02

    規則要進版本控制。代理內建的記憶存在個人機器上、跟著單一供應商走，隊友拿不到。

  • 03

    最高投報率的一條是可驗證的迴圈：測試、型別、截圖、延遲上限，讓代理能自己判斷「做完了」。

  • 04

    不是所有規範都該進來。安全審查與品質檢核屬於技能，在拉取請求階段才執行，不必常駐上下文。

先講成本

它跟一般文件的差別，在於它一直都在

README 只有人去讀它的時候才有成本；CLAUDE.md 不一樣，它會被附加到每一次送出的提示裡。這代表兩件事同時成立：你寫進去的規則會被穩定執行，而你寫進去的廢話也會被穩定重讀。大型語言模型（Large Language Model，LLM）在上下文變長時遵循指令的表現會下滑，這點已經被反覆驗證，所以把整份專案文件倒進來，實際效果通常是負的。

務實的做法是設一個明確的行數上限，抓在 500 行左右。內容超出就往兩個方向拆：目錄層級的巢狀 CLAUDE.md，只在代理實際碰到那個子目錄時才載入；以及技能，把整套流程收成一個可被呼叫的單元，需要時才展開。這樣主檔案維持精簡，細節也沒有消失。

另外值得一提的是可攜性。若同時使用其他工具鏈，CLAUDE.md 與 AGENTS.md 的角色是等價的，內容基本可以互換。挑一個當正本、另一個做軟連結，就不必維護兩份會慢慢分岔的規則。

十二條規則

每一條，都是某次代理犯錯留下的疤

01Journal

讓檔案自己長大

第一次就寫出完美的 CLAUDE.md 是不可能的。這是一份活文件：你會在使用過程中一路撞見代理的錯誤判斷、規則的缺口、講不清楚的地方，然後才知道該補什麼。問題是「請把這條規則加進 CLAUDE.md」這件事若要人手動觸發，多半就不會發生。

Terraform、Vagrant 與 Ghostty 的作者 Mitchell Hashimoto 把 AGENTS.md 當成失敗日誌在維護：檔案裡的每一行，都對應到代理至少犯過一次的具體錯誤。用他自己的說法，那份檔案的每一行都源自一次不良的代理行為，而寫下來之後幾乎都被根治了。這個標準很好用，因為它同時是新增規則的門檻，也是刪除規則的理由——想不起來是哪次失敗催生的那行，就該刪掉。

把這件事本身做成規則，再配一個對應的技能，整個流程就能自動化：代理犯錯、你指出來、它順手把教訓寫回檔案。至於「代理不是已經有記憶功能了嗎」——有，但預設存在你個人機器上、不進專案的版本控制，而且綁定單一供應商，換工具或換隊友就帶不走。規則要能被審閱、被 diff、被回溯，就得放進儲存庫。

起因同一類錯誤在不同的對話裡反覆出現，每次都要人重新用提示糾正一遍。
寫進檔案當使用者指出錯誤或給出新的偏好，主動把對應規則追加到本檔案，並在提交訊息中註明來源。
02Tests

定義一個代理跑得動的測試迴圈

這是投資報酬率（Return on Investment，ROI）最高的一條。測試驅動開發（Test-Driven Development，TDD）真正的價值不在測試本身，而在於它逼代理先回答一個問題：「做完」長什麼樣子？ 沒有這個定義，代理只能自我感覺良好地宣布一切看起來都沒問題；有了它，代理就能系統性地驗證自己的產出、涵蓋邊界情況、在失敗時知道要回頭改哪裡。

這也是「憑感覺寫程式」與「代理式工程」的分界線。會迭代的代理產出的程式碼，品質明顯高於一次成型的版本，而迭代要能收斂，必須有一個誠實的訊號告訴它現在是好是壞。把測試指令、涵蓋率門檻、以及「未通過就不得宣告完成」這件事明確寫進檔案，代理才有東西可以繞著跑。

規模化之後這個效果會非常明顯。以代理把 PostgreSQL 用 Rust 重寫的 pg-rust 專案為例，之所以做得起來，關鍵是他們手上有一套約四萬六千項的測試當作正確性的關卡——代理可以自由地大改，因為每一步都有辦法被判定對錯。

起因代理宣稱功能已完成，實際上沒跑過任何測試，錯誤在下一輪才被人工發現。
寫進檔案先寫測試再寫實作。完成任務前必須執行完整測試指令並貼出輸出；有任何失敗就不算完成。
03Questions

遇到模糊就問，不要自己補完

臆測是代理最惱人的失敗模式。只要提示裡留下任何模糊空間，代理就可能對你的意圖做出很有創意的假設，然後基於那個假設一路往下蓋。糟糕的地方在於錯誤會被放大：走偏的方向愈往後走，回頭的成本愈高，而且中途看起來一切都很順利。

你永遠不會寫出完美的提示或規格，所以真正該做的是把「發現歧義時停下來確認」變成預設行為。這條規則的成本很低——多一輪問答——但它擋掉的是整段被丟棄的實作。實務上可以再加一個限制條件：問題要一次問完、要具體、而且要附上你傾向的預設選項，避免代理用一連串瑣碎的問題把節奏打斷。

起因需求描述含糊，代理自行選定一種解釋並完成整個功能，方向與預期不符。
寫進檔案需求有多種合理解讀時，先提出具體問題並附建議選項，取得確認後再動工，不得自行假設。
04Types

型別開到最嚴，而且一開始就開

TypeScript 近期成為 GitHub 上使用最廣的語言，很大一部分原因是代理在有型別的環境裡表現明顯更好。型別是一種免費的驗證迴圈：它在不必額外寫測試的情況下就能攔下大量錯誤，並且把模組之間的契約固定下來，讓代理不需要把整個呼叫鏈讀完才敢改一個函式。

重點是「一開始就開」。如果不把嚴格模式與禁用 any 這件事寫進檔案，代理會先產出一堆鬆散的程式碼，等到型別檢查失敗才回頭修，過程中通常還會用型別斷言把問題蓋掉。與其事後清理，不如讓它從第一行就受約束。同樣的邏輯適用於任何具備型別系統的語言，也適用於程式碼檢查工具與格式化設定。

起因代理大量使用 any 與型別斷言換取編譯通過，把錯誤推遲到執行期。
寫進檔案嚴格模式全開，禁止 any 與非空斷言。型別檢查與程式碼檢查必須零錯誤，不得以忽略註解繞過。
05Packages

只用有人在維護的套件

程式碼的生產成本已經趨近於零，但維護成本沒有跟著降。代理的預設傾向是自己刻——與其安裝一個現成套件，它更願意在你的專案裡多寫三百行。多數情況下這是壞交易：那三百行從此變成你要維護的資產，而它取代的是一個被數萬個專案驗證過的實作。

反過來也要設防。這一年來供應鏈攻擊頻繁，讓代理自由安裝任何套件等於把安裝權限外包出去。合理的門檻很簡單，而且代理有能力自己查核：足夠的下載量、近期仍有實質提交（最近幾週有推送而不是三年前的最後一版）、以及套件名稱與你要的功能確實吻合，避免打字相似的仿冒套件。把這些條件寫成可判定的規則，代理才不會憑印象決定。

起因代理為了一個小需求自行實作既有函式庫的功能；或反過來安裝了長期無人維護的冷門套件。
寫進檔案優先採用成熟套件而非自行實作；安裝前確認下載量、最近數週的提交紀錄與套件名稱正確性，並向使用者說明理由。
06Naming

命名先講好，之後就不用吵

跟一群人合作一樣，代理在不同的日子會給你不同的詞。使用者介面（User Interface，UI）上可能同時出現「登入」、「登錄」、「Sign in」；程式碼裡可能同時存在 deleteUser 與 removeProduct 兩種語意相同的動詞。這件事在一開始就掐掉最便宜。

把使用者可見的文案用語與內部程式碼命名分成兩份清單，各自給定規則：動詞怎麼選、大小寫怎麼寫、檔名與元件名的形式、布林值的前綴。一致性不只是人類維護起來比較舒服，它也直接改善代理對程式碼庫的推理能力——當同一個概念永遠用同一個字，代理就能靠搜尋找到全部相關位置，而不必逐檔閱讀去猜。

起因同一個動作在不同畫面與不同函式中被叫成三種名字，搜尋找不齊，重構時漏改。
寫進檔案附一份動詞與名詞對照表，涵蓋介面文案與程式碼識別字；新增名稱前先確認表中是否已有既有用法。
07Structure

專案結構寫薄薄一層就夠

代理光看檔案樹就能推論出大部分結構，所以這一段不需要巨細靡遺，反而要克制。真正值得寫的是推論不出來的約定：新的路由該放哪、共用元件與單頁專用元件如何區分、資料存取層允許被誰匯入、哪些目錄是產生出來的不可手改。

這是一筆很便宜的一致性投資。少了它，代理每次要決定檔案位置時都得重新掃一遍專案，既慢又不穩定；有了它，同一個決定每次都會落在同一個地方。判斷標準很簡單：如果某段結構描述只是在複述 ls 的輸出，就刪掉。

起因同性質的檔案被放到三個不同目錄，因為每次判斷位置的依據都不一樣。
寫進檔案列出目錄職責與匯入方向限制，標明產生檔不得手動編輯；只寫檔案樹看不出來的部分。
08Hands-on

讓它像人一樣把應用程式點過一遍

單元測試全綠不代表產品能用。完成一個較大的功能之後，應該真的操作一次——這件事過去昂貴到需要一整組品質保證（Quality Assurance，QA）人力，現在代理可以自己開瀏覽器、啟動行動裝置模擬器，照著真實使用者的路徑一步步點下去。

這種操作會揪出標準測試看不見的問題：競爭條件、按鈕連點兩次、切換分頁後回來狀態不對、非快樂路徑上的空狀態。值得強調的是，這裡指的不是叫代理去寫一整套端對端（end-to-end，E2E）測試程式——那是另一件事，也有它的成本。這條規則要的只是親手操作一遍，把觀察到的異常回報出來。

起因測試全數通過，但功能在真實操作流程中第二步就卡住，沒有任何測試涵蓋該路徑。
寫進檔案完成較大功能後，實際啟動應用程式並以使用者路徑操作一次，含錯誤與空狀態，回報所見問題。
09Visuals

截一張圖，用真實資料

這條接著上一條。你可以有滿版的綠色勾勾，同時有人在 body 上留了一行 opacity: 0——所有測試都會通過，畫面全白。要求代理截圖並實際檢視自己的產出，這類樣式錯誤才會浮出來。

更關鍵的是載入真實資料。用假文排版的畫面幾乎永遠是完美的，因為假文的長度剛剛好。換成真實內容之後，過長的標題會撐破容器、空字串會讓卡片塌陷、極端數值會把表格推到畫面外。把「檢視時必須使用具代表性的真實資料，包含最長與最空的情況」寫進規則，代理才會去測那些真的會壞掉的邊界。順帶把行動裝置寬度、鍵盤焦點與深淺色模式一起列進檢查項，成本幾乎為零。

起因版面在假文下完美，換上真實內容後標題溢出、卡片高度不一，代理從未實際看過畫面。
寫進檔案介面變更後截圖檢視，使用真實資料並涵蓋最長內容與空狀態，另檢查行動裝置寬度與鍵盤焦點。
10Latency

給延遲一個數字，工作往資料庫推

有個經典的失敗長這樣：代理從資料庫撈出一千列，然後在應用程式層用迴圈過濾出它要的三列。這件事即使在最新的前沿模型上仍然會發生，因為在沒有約束的前提下，那個寫法確實比較好寫。

最簡單的解法是給一個可被檢查的數字：每一個應用程式介面（Application Programming Interface，API）端點的回應時間上限，例如 200 毫秒。有了上限，代理就有理由去量測，而不是憑感覺。再往前一步，把偏好也寫清楚——能在資料庫做的就不要拉回應用層、只取需要的欄位、避免 N+1 查詢、對過濾與排序欄位檢查索引。這種針對關鍵路徑的快速檢查通常只花幾分鐘，卻經常換到數十倍甚至百倍的差距，因為原始寫法的問題往往非常基本。

起因代理在應用層過濾整張資料表，端點回應時間隨資料量線性惡化。
寫進檔案端點回應時間上限 200 毫秒。過濾、彙總與排序在資料庫完成，只取必要欄位，並確認相關索引存在。
11Errors

錯誤要早失敗、大聲失敗

錯誤被吞掉的地方，就是缺陷滲進系統的地方。空的 catch 區塊、只印一行「哎呀出錯了」的處理、把失敗當成空陣列往下傳——這些寫法都會讓問題在離現場很遠的地方才爆炸，而那時候已經很難查了。

預設策略應該是早失敗、失敗得徹底；只有在確實能復原的情況下才捕捉，而且要在原地處理完。回傳給用戶端的訊息則要具體有用：說明發生了什麼、下一步能做什麼，不要道歉、不要含糊。這一段特別適合在 CLAUDE.md 裡指向實際檔案——錯誤型別定義在哪、記錄器怎麼用、哪些欄位不得寫進日誌、正式環境的錯誤要送到哪裡。指路比複述規則有效，也省行數。

起因例外被空的 catch 吞掉，錯誤在數層之外以難以理解的形式出現，日誌中查無紀錄。
寫進檔案禁止吞掉例外；無法復原就往上拋。錯誤型別與記錄方式見指定檔案，用戶端訊息須說明原因與後續動作。
12Index

把反覆探索的答案直接寫下來

每開一個新的對話，代理就得重新認識你的專案一次。若它每次都要靠搜尋才能找到驗證邏輯放在哪、事件是怎麼流動的、哪一層負責交易邊界，那些探索的代價你每次都在付——花時間、花上下文，而且結論未必每次都一樣。

解法是一段簡短的系統設計說明，加上一張查詢表：概念對應到檔案路徑。這裡的判準相當明確——如果你發現代理一再為了同一件事去翻程式碼，那件事就該被寫進 CLAUDE.md。反過來說，只被查過一次的東西不必寫。這條規則同時也是控制檔案膨脹的機制，因為它把「值不值得佔用每一輪的上下文」變成一個可以觀察的問題。

起因每個新對話開頭都花大量步驟重新搜尋同一批檔案，才能開始真正的工作。
寫進檔案附一段架構概述與「概念 → 檔案路徑」查詢表；代理重複探索同一主題時，把結論補進表中。

邊界

有些規範，放進來反而是浪費

安全審查、更嚴格的程式碼品質檢核、無障礙稽核、相依套件盤點——這些當然都該做，但它們不必常駐在每一輪對話裡。它們是階段性的流程，適合收成技能，在拉取請求（Pull Request，PR）階段才被明確呼叫執行。放進 CLAUDE.md 只會有兩個結果：平時佔著上下文，真正需要時卻因為描述太簡略而做不徹底。

區分的方式可以很直接：「每一次都適用」的約束留在 CLAUDE.md，「特定時機才執行」的流程做成技能。前者是背景常識，後者是可被呼叫的動作。同理，冗長的樣板程式碼、完整的資料庫綱要、逐條的介面文件，都屬於指路就好、不必內嵌的類型。

最後值得說清楚的是，上面這 12 條不是戒律。有些團隊不需要嚴格型別，有些產品沒有介面可截圖，有些專案的效能瓶頸根本不在資料庫。這份檔案的權威來自它是否真的擋掉了你遇過的失敗，而不是它抄得多完整。
