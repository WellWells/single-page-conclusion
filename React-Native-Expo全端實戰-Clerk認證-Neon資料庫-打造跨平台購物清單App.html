🧭 本文重點

🧱 前置需求與成本的誠實檢驗

這份教學要做的是一個叫 Grocify 的購物清單應用程式：登入之後可以新增品項、勾選完成、調整數量、看統計、清除已完成，還能按一顆按鈕把問題回報給開發者。它同時跑在 iOS 與 Android 上，資料存在雲端 Postgres，而且是完整的前後端——後端就寫在同一個專案裡。

技術堆疊鎖定 Expo SDK 54。刻意不用最新版：NativeWind v4、Clerk、Drizzle 這一整套生態在 54 上最穩定，而更新的 SDK 每一版都在搬動路由與分頁的 API。本文所有版本號都是實際查證過的（npm dist-tag 與 Expo 的 bundledNativeModules.json），不是憑印象寫的。

🧭 React Native 與 Expo：觀念先釐清

React Native 是一個框架，讓開發者用 React（JavaScript 或 TypeScript）撰寫真正的原生行動應用程式。它的價值在於跨平台：寫一份程式碼，同時在 iOS 與 Android 上執行。在它出現之前，iOS 要學 Swift 或 Objective-C，Android 要學 Java 或 Kotlin，兩套程式碼、兩個團隊、兩倍的維護成本。

但光有 React Native 並不夠。React Native 的官方文件現在直接寫著：「我們相信體驗 React Native 的最佳方式是透過一個框架」，並且推薦 Expo。這兩者不是同一件事，而是上下層的關係：

React NativeExpo
定位核心框架（渲染引擎、原生橋接）建構在 React Native 之上的平台
提供什麼View、Text、FlatList 等核心元件與原生模組系統檔案路由、最佳化過的元件、原生模組生態系、雲端建置、空中更新（OTA）、伺服器路由
類比ReactNext.js

這個類比很精確：用 Next.js 的時候，本質上還是在寫 React，只是多了檔案路由、最佳化的圖片元件、伺服器端能力。用 Expo 的時候，本質上還是在寫 React Native。Coinbase、Bluesky 這類產品都是用 Expo 上架的，它完全是生產級的。

React 網頁與 React Native 的對照

有 React 基礎的人，八成的知識可以直接搬過來。剩下兩成的差異是這張表，值得先看過一遍——後面的程式碼會不斷用到：

網頁上寫的React Native 要寫的關鍵差異
<div><View>flexDirection 預設是 column，不是 row（網頁是 row）。而且 View 裡不能直接放裸字串。
<span>、<p>、<h1><Text>所有文字都必須被 <Text> 包住。裸放字串會直接崩潰：Text strings must be rendered within a <Text> component。
<img src="..."><Image>（用 expo-image）Expo 的版本有磁碟快取、contentFit（等同 CSS 的 object-fit）、淡入動畫、BlurHash 佔位縮圖。React Native 內建的 Image 這些都沒有。
className 或 CSS 檔style={styles.x} + StyleSheet.create()沒有 CSS 檔、沒有層疊、沒有繼承（子元件不會繼承父層字級）。單位是無單位數字（dp），沒有 px／rem。第 4 章的 NativeWind 會把 className 加回來。
onClickonPress對應元件是 <Pressable>（現行推薦）。TouchableOpacity 仍能用，但屬於舊 API。
items.map(i => <Row />)<FlatList data renderItem keyExtractor />.map() 會一次把一千筆全部建成原生 View，記憶體直接爆掉。FlatList 只渲染可視範圍並回收捲出畫面的列。絕對不要把 FlatList 包在 ScrollView 裡。
<form> + <input onChange><TextInput value onChangeText> + <Pressable>沒有 form、沒有 button、沒有 onSubmit。表單就是一堆受控 TextInput 加一顆 Pressable。注意是 onChangeText（直接給字串），不是 onChange。
<a href="/x"><Link href="/x">來自 expo-router。命令式導覽用 useRouter()：push／replace／back。
沒有安全區的概念useSafeAreaInsets()瀏海、狀態列、Home Indicator 會蓋住內容。React Native 內建的 SafeAreaView 已被官方標為棄用，而且只在 iOS 有效。

⚠️ 最常見的第一個 bug：內容被狀態列或瀏海蓋住。十之八九是因為 import { SafeAreaView } from 'react-native'——那個版本已棄用，而且在 Android 上完全不處理狀態列。正解是從 react-native-safe-area-context 匯入，或用 useSafeAreaInsets() 自己把 insets.top 加進標題的 paddingTop。使用 Expo Router 時不要自己再包一層 SafeAreaProvider，Router 已經包好了。

🏗️ 專案初始化與檔案結構契約

先建立專案。務必明確釘住 SDK 版本——不加 --template default@sdk-54 的話，拿到的版本會隨著 Expo 的過渡期政策漂移，本文所有的 API 就對不上了。

# 1. 建立專案（一定要釘住 SDK 版本）
npx create-expo-app@latest Grocify --template default@sdk-54
cd Grocify

# 2. 清空模板範例（會問 Y/n，回答 y）
npm run reset-project
rm -rf app-example

# 3. ★ 刪掉 reset-project「重新產生」的 app/index.tsx
#    這一步漏掉，本章必定失敗（見下方陷阱）
rm app/index.tsx

# 4. 把路由根目錄搬到 src/app，建立目錄骨架
mkdir -p "src/app/(auth)" "src/app/(home)" src/components src/hooks src/lib src/store src/types
mv app/_layout.tsx src/app/_layout.tsx
rmdir app          # ★ 根目錄不能留下 app/，否則 Expo Router 會忽略 src/app

# 5. 清掉用完即丟的 reset 腳本
rm -rf scripts     # 順手把 package.json 的 "reset-project" script 那行刪掉

# 6. 安裝開發建置需要的套件
npx expo install expo-dev-client

# 7. 健檢
npx expo install --check
npx expo-doctor

💣 陷阱一：reset-project 會「重新生出」一個 app/index.tsx

這個腳本把模板檔案搬到 app-example/ 之後，會寫入一個全新的 app/index.tsx（就是那句「Edit app/index.tsx to edit this screen.」）。不刪掉它，它會和 src/app/(home)/index.tsx 搶同一個網址 /（括號資料夾不進 URL）。結果是 App 開起來顯示那句佔位文字，看起來像「我的程式碼沒生效」，極難聯想到原因。

陷阱二：根目錄不能同時存在 app/ 與 src/app/。Expo Router 兩者都支援，但根目錄的 app/ 優先權較高。只要根目錄還留著 app/（哪怕是空的），src/app/ 會被完全忽略，而且不會有任何錯誤訊息。搬完一定要 rmdir app。

關鍵欄位，以及那些刻意不寫的東西：

欄位為什麼
scheme: "grocify"自訂 URL scheme。OAuth 回跳的命脈——沒有它，Google／Apple 登入完就回不來，而且不會有明顯錯誤。
bundleIdentifier／package模板沒有預設值，做開發建置前必填。填了什麼，Clerk 後台的回跳網址就要對應什麼。
web.output: "server"後端是 Expo Router API Routes，必須是 server 而不是 static。這是唯一讓 +api.ts 真的變成伺服器路由的開關。
softwareKeyboardLayoutMode: "pan"Android 在 edge-to-edge 之下 resize 有時不生效，pan 才穩。少了它，規劃頁的送出鈕會被鍵盤蓋住。
plugins 裡沒有 expo-blur／expo-glass-effect這兩個套件沒有 config plugin。寫上去，npx expo run:ios 會在解析設定的階段就死於 PluginError，Xcode 都還沒被叫起來。它們是自動連結模組，只要安裝、不要註冊。

沒有 @clerk/expo plugin只有做「原生 Google／Apple 登入」的加分關卡時才加。它會強制把 iOS 部署目標拉到 17.0，可能撞到其他 pod。

另外注意：newArchEnabled 與 android.edgeToEdgeEnabled 這兩個欄位在 SDK 55 起已被移除（新架構與 edge-to-edge 成為唯一選項）。之後若升級，記得刪掉，否則會變成 schema 錯誤。

Expo Router 用檔案結構決定路由，沒有 App.tsx、沒有手寫的 NavigationContainer。package.json 的進入點是 expo-router/entry，而 src/app/_layout.tsx 就是根佈局。

Expo Go 與開發建置：什麼時候該換

Expo Go 是一個預先做好的容器 App，掃 QR code 就能跑你的 JavaScript。它很方便，但它的原生執行檔裡只有 Expo 官方預先編進去的原生模組。一旦要用 Clerk 的原生登入、Sentry 的原生崩潰回報、或原生分頁列，Expo Go 就無能為力。

解法是開發建置（development build）：把你自己的原生模組編進一個屬於你的容器 App。指令是 npx expo run:ios 或 npx expo run:android——它會先做 prebuild（從 app.json 與 config plugin 產生 ios/、android/ 資料夾），編譯，安裝，然後啟動 Metro。第一次要等幾分鐘，之後改 JavaScript 都是熱重載，不必重編。

本文的分界線很明確：第 2 到第 4 章（初始化、路由、NativeWind）在 Expo Go 裡就能預覽。從第 5 章（Clerk 的原生 OAuth）開始，Grocify 不再支援 Expo Go，開發一律 npx expo run:ios ／ npx expo run:android。

附帶一個容易困惑的行為：裝了 expo-dev-client 之後，npx expo start 預設就是開發建置模式，終端機的 QR code 不再是給 Expo Go 掃的。這時拿 Expo Go 去掃會看到 Failed to download remote update。想退回 Expo Go 必須明確加 --go。

ios/ 與 android/ 這兩個資料夾是 prebuild 產生的，模板的 .gitignore 預設就忽略它們。這叫做持續原生生成（Continuous Native Generation，CNG）：原生專案是設定的產物，不是要手動維護的程式碼。改了 app.json 的原生欄位（icon、plugins、權限），一定要 npx expo prebuild --clean 重新產生，熱重載不會更新原生設定。

💣 src/ 版面的兩個路徑陷阱（互相牽制，很容易修好一邊弄壞另一邊）

1. content glob：官方文件預設的 ["./App.tsx", "./components/**/*"] 在這個專案裡一個檔案都比對不到。沒被比對到就不編譯，畫面完全沒有樣式，而且零錯誤訊息。必須是 ['./src/**/*.{js,jsx,ts,tsx}']。

2. CSS 匯入路徑：global.css 在專案根目錄，而根佈局在 src/app/——所以要往上兩層：import '../../global.css'。同時 metro.config.js 的 input: './global.css' 是相對專案根、不跟著改。兩邊指的必須是同一個檔案，否則 Tailwind 編了一個檔、你匯入了另一個檔，所有 className 靜靜地全部失效。

深色模式：端到端做完

深色模式常見的半套做法是「只寫 dark: 那一半」。React Native 沒有 CSS 的層疊繼承，dark:text-gray-100 沒有配對的 text-gray-900，淺色模式就完全沒有顏色。顏色類別一律成對寫。半套的深色模式（背景黑了、文字也是黑的）比沒有更糟。

📄 Grocify/src/hooks/useThemePreference.ts

import { useCallback, useEffect, useState } from 'react';
import AsyncStorage from '@react-native-async-storage/async-storage';
import { useColorScheme } from 'nativewind'; // ★ 一定要從 'nativewind'，不是 'react-native'

export type ThemePreference = 'light' | 'dark' | 'system';

const STORAGE_KEY = 'grocify.theme-preference';

function isThemePreference(value: string | null): value is ThemePreference {
  return value === 'light' || value === 'dark' || value === 'system';
}

/**
 * - preference：使用者「選的」（light / dark / system），持久化在 AsyncStorage。
 * - colorScheme：NativeWind 解析後「實際生效」的配色。
 *   dark: 類別、StatusBar、任何條件判斷，都看 colorScheme，不要看 preference。
 * - hydrated：AsyncStorage 是非同步的。還沒讀完就 render，
 *   會先閃一下淺色再跳成深色。
 *
 * useColorScheme 必須從 'nativewind' 匯入：
 * React Native 自己的那個是唯讀的，驅動不了 dark: 類別，
 * 而且 setColorScheme() 在 tailwind 的 darkMode: 'media' 之下會直接 throw。
 */
export function useThemePreference() {
  const { colorScheme, setColorScheme } = useColorScheme();
  const [preference, setPreferenceState] = useState<ThemePreference>('system');
  const [hydrated, setHydrated] = useState(false);

  useEffect(() => {
    let cancelled = false;

    (async () => {
      try {
        const stored = await AsyncStorage.getItem(STORAGE_KEY);
        if (cancelled) return;
        const next: ThemePreference = isThemePreference(stored) ? stored : 'system';
        setPreferenceState(next);
        setColorScheme(next);
      } catch {
        // 讀不到就跟隨系統，不要因為 storage 壞掉就整個 App 起不來。
        if (!cancelled) setColorScheme('system');
      } finally {
        if (!cancelled) setHydrated(true);
      }
    })();

    return () => { cancelled = true; };
  }, [setColorScheme]);

  const setPreference = useCallback(
    (next: ThemePreference) => {
      // 先改 UI（同步、無延遲），再寫入 storage（失敗也不影響當下這一輪）。
      setPreferenceState(next);
      setColorScheme(next);
      void AsyncStorage.setItem(STORAGE_KEY, next).catch(() => {});
    },
    [setColorScheme],
  );

  return { preference, colorScheme, setPreference, hydrated };
}

還有一個容易漏的設定：app.json 必須有 "userInterfaceStyle": "automatic"。少了它，Expo 永遠回報 light，「跟隨系統」永遠是淺色。

怎麼證明這一層真的能動

動作預期可觀察結果

  const [emailAddress, setEmailAddress] = useState('');

    setFormError(null);

    const { error: verifyError } = await signUp.verifications.verifyEmailCode({ code });
    if (verifyError) {
      setFormError(verifyError.message ?? '驗證碼不正確');
      return;
    }

    // ★ 不要用 `if (signUp.status === 'complete')` 當 finalize 的閘門。
    //   signUp 是 signals 快照，await 之後那一行讀到的可能還是舊值，
    //   finalize() 就永遠不會被呼叫 —— 使用者信箱驗證成功了、卻沒登入，
    //   而且畫面沒有任何提示。
    //
    // ★ finalize() 才是真正「讓 session 生效」的動作（相當於 Core 2 的 setActive）。
    //   少了它，status 會變 complete，但使用者永遠沒登入，完全不報錯。
    const { error: finalizeError } = await signUp.finalize({
      navigate: ({ session }) => {
        if (session.currentTask) return; // 例如組織選擇這類 session task
        router.replace('/');
      },
    });
    if (finalizeError) setFormError(finalizeError.message ?? '無法建立登入狀態');
  };

  const awaitingCode =
    signUp.status === 'missing_requirements' &&
    signUp.unverifiedFields.includes('email_address') &&
    signUp.missingFields.length === 0;

  // ── 驗證碼步驟 ──────────────────────────────────────────
  if (awaitingCode) {
    return (
      <View className="flex-1 justify-center gap-4 bg-white px-6 dark:bg-neutral-950">
        <Text className="text-2xl font-bold text-neutral-900 dark:text-white">去信箱收驗證碼</Text>
        <Text className="text-neutral-500">我們寄了一組 6 位數驗證碼到 {emailAddress}。</Text>

        <TextInput
          className="rounded-xl border border-neutral-300 px-4 py-3 text-lg tracking-[8px] text-neutral-900 dark:border-neutral-700 dark:text-white"
          value={code}
          placeholder="123456"
          placeholderTextColor="#9ca3af"
          keyboardType="number-pad"
          maxLength={6}
          onChangeText={setCode}
        />
        {errors.fields.code ? (
          <Text className="text-sm text-red-600">{errors.fields.code.message}</Text>
        ) : null}
        {formError ? <Text className="text-sm text-red-600">{formError}</Text> : null}

        <Pressable
          className="items-center rounded-xl bg-emerald-600 py-4 active:opacity-80"
          disabled={isBusy || code.length < 6}
          onPress={onVerifyPress}
        >
          {isBusy ? <ActivityIndicator color="#fff" /> : <Text className="font-semibold text-white">驗證</Text>}
        </Pressable>

        <Pressable onPress={() => void signUp.verifications.sendEmailCode()}>
          <Text className="text-center text-emerald-600">重寄一次</Text>
        </Pressable>
      </View>
    );
  }

  // ── 帳密步驟 ────────────────────────────────────────────
  return (
    <View className="flex-1 justify-center gap-4 bg-white px-6 dark:bg-neutral-950">
      <Text className="text-3xl font-bold text-neutral-900 dark:text-white">建立 Grocify 帳號</Text>

      <TextInput
        className="rounded-xl border border-neutral-300 px-4 py-3 text-neutral-900 dark:border-neutral-700 dark:text-white"
        autoCapitalize="none"
        autoComplete="email"
        keyboardType="email-address"
        value={emailAddress}
        placeholder="you@example.com"
        placeholderTextColor="#9ca3af"
        onChangeText={setEmailAddress}
      />
      {/* ★ 欄位錯誤的 key 不對稱：註冊是 emailAddress，登入是 identifier。
          寫錯就是錯誤訊息永遠不顯示，而且不會報錯。 */}
      {errors.fields.emailAddress ? (
        <Text className="text-sm text-red-600">{errors.fields.emailAddress.message}</Text>
      ) : null}

      <TextInput
        className="rounded-xl border border-neutral-300 px-4 py-3 text-neutral-900 dark:border-neutral-700 dark:text-white"
        secureTextEntry
        value={password}
        placeholder="密碼"
        placeholderTextColor="#9ca3af"
        onChangeText={setPassword}
      />
      {errors.fields.password ? (
        <Text className="text-sm text-red-600">{errors.fields.password.message}</Text>
      ) : null}

      {errors.global?.length ? (
        <Text className="text-sm text-red-600">{errors.global[0].message}</Text>
      ) : null}
      {formError ? <Text className="text-sm text-red-600">{formError}</Text> : null}

      <Pressable
        className="items-center rounded-xl bg-emerald-600 py-4 active:opacity-80"
        disabled={isBusy || !emailAddress || !password}
        onPress={onSignUpPress}
      >
        {isBusy ? <ActivityIndicator color="#fff" /> : <Text className="font-semibold text-white">註冊</Text>}
      </Pressable>

      <SocialAuthButtons />

      <View className="flex-row justify-center gap-1">
        <Text className="text-neutral-500">已經有帳號了？</Text>
        <Link href="/(auth)/sign-in">
          <Text className="font-semibold text-emerald-600">登入</Text>
        </Link>
      </View>

      {/* ★★★ 註冊頁「必須」有這個節點 ★★★
          Clerk 的機器人防護（Smart CAPTCHA）預設開啟，
          它會把 widget 掛進 nativeID="clerk-captcha" 的 View。
          少了它 → 註冊 100% 失敗。 */}
      <View nativeID="clerk-captcha" />
    </View>
  );
}

登入頁的結構幾乎一樣，只是流程更短：signIn.password({ emailAddress, password }) → signIn.finalize({ navigate })。唯一要注意的是欄位錯誤的 key 不對稱：登入頁的 email 欄位錯誤在 errors.fields.identifier，註冊頁在 errors.fields.emailAddress。

import { AuthView, UserButton } from '@clerk/expo/native';
import { useState } from 'react';
import { Button, Modal, View } from 'react-native';

export function NativeAuthPanel() {
  const { isSignedIn } = useAuth({ treatPendingAsSignedOut: false });
  const [authOpen, setAuthOpen] = useState(false);

  return (
    <View className="flex-1 gap-4 bg-white px-6 pt-16 dark:bg-neutral-950">
      {isSignedIn ? <UserButton /> : <Button title="登入" onPress={() => setAuthOpen(true)} />}

      <Modal
        animationType="slide"
        visible={authOpen}
        presentationStyle="pageSheet"
        onRequestClose={() => setAuthOpen(false)}
      >
        {/*
          AuthViewProps 實際只有三個：
            mode?: 'signIn' | 'signUp' | 'signInOrUp'   （預設 'signInOrUp'）
            isDismissible?: boolean
            onDismiss?: () => void
          ⚠️ 沒有 'both' 這個值 —— 很多教學講的 mode="both" 是錯的。
          AuthView 是 inline 渲染、撐滿 parent，它「不會自己彈出來」，所以要自己包 Modal。

⚠️ 這個元件刻意不做成路由。Expo Router 用 require.context 建路由樹，會在啟動時立即載入每一個路由模組。只要 src/app/(auth)/native-auth.tsx 存在，@clerk/expo/native 就會在 App 啟動時被執行——即使使用者從沒點進去——於是在 Expo Go 裡整包 App 直接紅屏（Cannot find native module）。放在 src/components/，由你決定何時渲染。

🛡️ 架構關鍵：祕密絕不上手機

這一節是全文最重要的一節。

命題只有一句：手機 App 是公開的二進位檔，任何寫進 bundle 的東西都等於公開發佈。

網路上大量「Expo + Drizzle + Neon」教學會直接在畫面裡 import { db }，並使用 EXPO_PUBLIC_DATABASE_URL。那等於把資料庫的擁有者密碼發給每一位使用者。Demo 影片裡它會動——這正是陷阱所在。能跑，不等於安全。

先做一次實驗，你就永遠不會忘記

# .apk / .ipa 就是 zip 檔
unzip -o app-release.apk -d apk-out
strings apk-out/assets/index.android.bundle | grep -iE 'postgres|sk_test|sk_live|neon\.tech'

手機上的 JavaScript bundle，本質上是「已經下載到攻擊者電腦裡的一份檔案」。沒有任何「只有我們的 App 讀得到」這種東西存在。混淆不算防護——連線字串是一串必須原樣送出去的字元，它一定得在某處以明碼存在。Hermes 是 bytecode，但字串常數依然是明碼，所以 strings 撈得到。編譯不等於加密。

推論鏈很短：

  1. 連線字串進了 bundle → 任何人拿得到。
  2. 任何人拿到 postgresql://user:pass@ep-xxx.neon.tech/neondb → 他可以直接連你的 Neon。
  3. 他連上你的資料庫 → 他讀得到所有使用者的購物清單，也可以 DROP TABLE。你程式裡那些 where(eq(items.userId, userId)) 一行都不會被執行到——因為他根本沒經過你的程式。

Neon 的連線字串帶的還是 neondb_owner（資料庫擁有者）。而且「補救成本」更慘：一旦 build 上架，金鑰已經散佈在每一位使用者的裝置上，唯一補救是輪替 Neon 密碼並強制所有人更新——那就是一次資安事故。

EXPO_PUBLIC_ 的真正意義

Metro 在打包時，會把程式碼裡出現的 process.env.EXPO_PUBLIC_XXX 做字串取代，把值直接寫進 bundle。這不是「執行期讀環境變數」，是編譯期把值烙進去。

意義
有 EXPO_PUBLIC_ 前綴我聲明「這個值是公開的，我知道它會被印在 bundle 裡」。
沒有前綴這個值永遠不會出現在 client bundle；App 端讀到的是 undefined。只有 +api.ts 執行時的伺服器行程讀得到。
絕對禁止放進 EXPO_PUBLIC_外洩後果
DATABASE_URL等同資料庫 root 權限，可讀他人資料、可 DROP TABLE。
CLERK_SECRET_KEY（sk_…）可代表任何使用者簽發／撤銷 session，等同全站帳號淪陷。
SENTRY_AUTH_TOKEN可讀寫你的 Sentry 專案。
任何 OAuth client secret、任何第三方 server key、任何私鑰同上。
可以放（設計上就是公開的）說明
EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY（pk_…）名字就叫 publishable。
EXPO_PUBLIC_SENTRY_DSN設計為公開，只允許送出事件。
EXPO_PUBLIC_API_URL就是一個網址，抓一次封包就有。

⚠️ 兩個要糾正的迷思

1.「我不加前綴就安全了」——只對了一半。不加前綴的變數在 client 端讀出來是 undefined（所以 App 會壞，不會洩漏）。但只要有一支被畫面元件 import 的模組讀了它，那支模組就會被打包進 client bundle。安全靠的是檔案邊界（src/lib/server/ 只被 +api.ts 匯入），不只是靠命名。

2.「EAS 的 secret 可見度可以把機密藏進 App」——不行。只要值被 Metro 內嵌進 bundle，不管你在 EAS 標成什麼，它就是公開的。EAS 的可見度標籤管的是「誰能在 EAS 平台上看到這個值」，不是「這個值會不會進 App」。

三條鐵律（全文從頭到尾不會違反）

  1. src/db/** 與 src/lib/server/** 只能被 src/app/api/**+api.ts 匯入。任何畫面 import 到它們，Metro 就會把 Neon driver 與被內嵌的連線字串一起打包進手機。
  2. 前端要用資料庫型別時，必須用 type-only import。import type { GroceryItem } from '@/types/grocery'。少了 type 這個字，整個 drizzle 執行期程式碼就會被拖進 App bundle——而 tsc 完全不會報錯。
  3. userId 永遠來自 payload.sub，永遠不從 request body 讀。body 是使用者可以任意編造的。

三種後端架構的取捨

本文主線用 Expo Router API Routes：零額外倉庫、零額外部署、與 App 共用 TypeScript 型別與路徑別名、一行指令上線。但誠實地把限制與遷移路徑寫出來，才是「教學」與「照抄」的差別：

Expo Router API Routes
（本文主線）		獨立 Hono / ExpressNeon Data API + RLS
部署expo export + eas deploy自己找 Fly／Railway／VPS無伺服器可部署（Neon 直出 REST）
型別共享直接共用需 monorepo 或手抄由 schema 推導

執行環境限制Cloudflare Workers（無 TCP，只能用 HTTP driver，沒有互動式交易）完整 Node不適用

為什麼不把 Neon Data API 當主線？它是「用戶端直連資料庫」還算安全的唯一做法——授權下沉到 Postgres 的資料列層級安全性（Row Level Security，RLS），JWT 由 Clerk 簽發、Neon 驗簽。但它有一個教學上的致命點：安全性完全押在「你有沒有正確寫 policy」，一個沒開 RLS 的表就是全表外洩，而且沒有任何程式碼可以 review。「忘記加 policy」比「忘記加 where」更難被發現。

-- 若走 Neon Data API 路線，這不是選配，是命脈：
ALTER TABLE items ENABLE ROW LEVEL SECURITY;
CREATE POLICY items_owner ON items
  FOR ALL
  TO authenticated
  USING (user_id = auth.user_id())
  WITH CHECK (user_id = auth.user_id());

遷移路徑要壓到「只改一個檔」。做法是：把「呼叫端」抽成一個 base URL（src/lib/api-url.ts），把「處理器」寫成純 Request → Response。真要搬到 Hono，+api.ts 裡的 GET／POST 幾乎可以原封不動貼進 Hono handler（兩邊都是 Web 標準的 Request／Response），App 端只要改 EXPO_PUBLIC_API_URL——那是可以公開的，它是網址，不是密鑰。

📄 Grocify/src/db/schema.ts

import { sql } from 'drizzle-orm';
import { boolean, index, integer, pgTable, text, timestamp, uuid } from 'drizzle-orm/pg-core';
import { createInsertSchema, createUpdateSchema } from 'drizzle-zod';
import type { z } from 'zod';

/**
 * items：一筆購物清單項目。
 *
 * userId 存的是 Clerk 的 user id（例如 "user_2abc..."），
 * 所以型別必須是 text —— 不是 uuid、不是 integer。
 *
 * 第二個 callback 回傳「陣列」是 drizzle-orm 0.36.0 起的官方寫法；
 * 舊的回傳物件寫法 { userIdIdx: index(...) } 從 0.36.0 起已被標為 deprecated。
 */
export const items = pgTable(
  'items',
  {
    id: uuid('id').primaryKey().default(sql`gen_random_uuid()`),
    userId: text('user_id').notNull(),
    name: text('name').notNull(),
    quantity: integer('quantity').notNull().default(1),
    // 「個 / 瓶 / 包」。規劃頁的表單、列元件與無障礙標籤都在用它。
    unit: text('unit').notNull().default('個'),
    category: text('category').notNull().default('other'),
    completed: boolean('completed').notNull().default(false),
    createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
    // $onUpdate 讓每次 UPDATE 自動刷新這個欄位，不必在每支 query 裡手動寫。
    updatedAt: timestamp('updated_at', { withTimezone: true })
      .notNull()
      .defaultNow()
      .$onUpdate(() => new Date()),
  },
  (table) => [
    // 每一次查詢都是 where user_id = ? order by created_at desc
    index('items_user_id_idx').on(table.userId),
    index('items_user_id_created_at_idx').on(table.userId, table.createdAt),
  ],
);

/* ---------- 型別推導（不必手寫 interface） ---------- */
export type Item = typeof items.$inferSelect;
export type NewItem = typeof items.$inferInsert;

/* ---------- drizzle-zod：從同一份 schema 產生驗證器 ---------- */

/** 新增項目時，前端只准送這四個欄位；userId 一律由伺服器從 Clerk token 取得 */
export const insertItemSchema = createInsertSchema(items, {
  name: (schema) => schema.trim().min(1, '品項名稱不可空白').max(80),
  quantity: (schema) => schema.int().min(1).max(999),
  unit: (schema) => schema.trim().min(1).max(10),
  category: (schema) => schema.trim().min(1).max(40),
}).omit({
  id: true,
  userId: true,      // ★ 就算 body 夾帶 userId 也會被 zod 剝掉
  completed: true,
  createdAt: true,
  updatedAt: true,
});

/**
 * 更新時所有欄位皆為 optional —— 但「一個欄位都沒給」必須擋掉。
 *
 * createUpdateSchema 讓每個欄位都變 optional，而 Zod 物件會把未知的 key 直接剝掉，
 * 所以 PATCH {} 與 PATCH { foo: 1 } 都會 safeParse 成功、data 都變成 {}；
 * 接著 db.update(items).set({}) 會擲出 "No values to set" → 一個沒人接的 500。
 * 用 .refine 在這一層就擋成 400。
 */
export const updateItemSchema = createUpdateSchema(items)
  .pick({ name: true, quantity: true, unit: true, category: true, completed: true })
  .refine((patch) => Object.keys(patch).length > 0, {
    message: '至少要提供一個要更新的欄位',
  });

export type InsertItemInput = z.infer<typeof insertItemSchema>;
export type UpdateItemInput = z.infer<typeof updateItemSchema>;

型別可以共用，程式碼不行

這支檔案是「安全宣稱」與「實作」之間最容易破功的縫隙。前端若寫成 import { items } from '@/db/schema'（少了 type），Metro 會把 drizzle-orm 與 @neondatabase/serverless 一起打包進 App bundle——而且 tsc 完全不會報錯。請開啟 ESLint 的 @typescript-eslint/consistent-type-imports 規則鎖死它。

第二個原因是型別會說謊：Response.json() 會把 timestamp 序列化成 ISO 字串，而 $inferSelect 給的是 Date。直接 re-export 等於前端拿到 string、TypeScript 卻以為是 Date，.getTime() 會在執行期炸。所以這份是「JSON 形狀」的手寫型別。

/**
 * ★ 這個檔案只能被 src/app/api/**+api.ts 匯入。★
 *
 * 每個函式的第一個參數都是 userId，且每一句 SQL 都帶 eq(items.userId, userId)。
 * 這是租戶隔離唯一的防線 —— 少寫一個 where，就是「A 讀得到 B 的清單」。
 */
import { and, count, desc, eq, sql } from 'drizzle-orm';

import { items } from '@/db/schema';
import type { InsertItemInput, Item, UpdateItemInput } from '@/db/schema';
import { db } from '@/lib/server/db';
import type { CategoryStat, ItemStats } from '@/types/grocery';

/* ============ READ ============ */

export async function getItems(userId: string): Promise<Item[]> {
  return db.select().from(items)
    .where(eq(items.userId, userId))
    .orderBy(desc(items.createdAt));
}

export async function getItem(userId: string, id: string): Promise<Item | null> {
  const [row] = await db.select().from(items)
    .where(and(eq(items.id, id), eq(items.userId, userId)))
    .limit(1);
  return row ?? null;
}

/* ============ CREATE ============ */

/** returning() 直接把寫入後的完整資料列拿回來（含 id / createdAt） */
export async function createItem(userId: string, input: InsertItemInput): Promise<Item> {
  const [created] = await db.insert(items).values({
    // ★ userId 來自 verifyToken 的 payload.sub，永遠不是 request body。★
    userId,
    name: input.name,
    quantity: input.quantity ?? 1,
    unit: input.unit ?? '個',
    category: input.category ?? 'other',
  }).returning();

  return created;
}

/* ============ UPDATE ============ */

/** where 一定要同時比對 userId，否則別人可以改你的資料。 */
export async function updateItem(
  userId: string,
  id: string,
  patch: UpdateItemInput,
): Promise<Item | null> {
  const [updated] = await db.update(items)
    .set(patch) // updatedAt 由 schema 的 $onUpdate 自動處理
    .where(and(eq(items.id, id), eq(items.userId, userId)))
    .returning();

  return updated ?? null;
}

/** 用 SQL 直接加減數量，避免「先讀再寫」的競態 */
export async function incrementQuantity(
  userId: string,
  id: string,
  delta: number,
): Promise<Item | null> {
  const [updated] = await db.update(items)
    .set({ quantity: sql`greatest(1, ${items.quantity} + ${delta})` })
    .where(and(eq(items.id, id), eq(items.userId, userId)))
    .returning();

  return updated ?? null;
}

/* ============ DELETE ============ */

export async function deleteItem(userId: string, id: string): Promise<Item | null> {
  const [deleted] = await db.delete(items)
    .where(and(eq(items.id, id), eq(items.userId, userId)))
    .returning();

  return deleted ?? null;
}

/** 「清除已完成」—— 一次 SQL 的批次刪除。陣列長度就是刪除筆數。 */
export async function clearCompleted(userId: string): Promise<number> {
  const deleted = await db.delete(items)
    .where(and(eq(items.userId, userId), eq(items.completed, true)))
    .returning({ id: items.id });

  return deleted.length;
}

/* ============ INSIGHTS 聚合 ============ */

/**
 * 一次 query 拿到總數／已完成／未完成三個數字。
 *
 * count() 由 drizzle-orm 匯出，會產生 count(*) 並自動 mapWith(Number)。
 * FILTER (WHERE ...) 是標準 Postgres 語法；
 * ★ ::int 是為了把 bigint 轉成 JS number ——
 *   不加的話你會拿到字串 "3" 而不是數字 3。★
 */
export async function getItemStats(userId: string): Promise<ItemStats> {
  const [row] = await db.select({
    total: count(),
    completed: sql<number>`count(*) filter (where ${items.completed})::int`,
    pending: sql<number>`count(*) filter (where not ${items.completed})::int`,
  }).from(items).where(eq(items.userId, userId));

  return row ?? { total: 0, completed: 0, pending: 0 };
}

/** 依分類 group by，給洞察畫面畫長條圖 */
export async function getStatsByCategory(userId: string): Promise<CategoryStat[]> {
  return db.select({
    category: items.category,
    total: count(),
    completed: sql<number>`count(*) filter (where ${items.completed})::int`,
  })
    .from(items)
    .where(eq(items.userId, userId))
    .groupBy(items.category)
    .orderBy(desc(count())) as Promise<CategoryStat[]>;
}

🔌 後端：Expo Router API Routes

把 app.json 的 web.output 設成 "server" 之後，src/app/ 底下任何叫做 xxx+api.ts 的檔案就變成伺服器路由。開發時它跑在 Metro dev server 上（可以直接 curl），正式版跑在 EAS Hosting 上。原生二進位檔本身沒有任何改變——後端不在手機上。

框架契約（已查證）
路由檔匯出 GET / POST / PATCH / PUT / DELETE，簽名是標準的 (request: Request)。沒匯出的方法 → 框架自動回 405；未捕捉的例外 → 自動 500。
動態片段是 handler 的第二個參數，不是 hook、不用自己 parse URL：export async function GET(request: Request, { id }: Record<string, string>)
src/app/ 底下每一個 .ts 都是路由，所以共用的輔助函式不能放 src/app/api/_auth.ts，要放 src/lib/server/。
API route 檔名不能有平台副檔名：items+api.web.ts 不會生效。

伺服器端驗證：把 token 換成 userId

💣 StatusError 的字串多載是個坑（實作與文件不符）

expo-server 的實作是：body = typeof body === 'object' ? JSON.stringify(body) : (body ?? ...)。也就是說 new StatusError(401, '缺少 token')（字串）會把裸字串當成 body，再配上 Content-Type: application/json 送出去——一個標成 JSON、內容卻不是 JSON 的回應。前端 await response.json() 會直接 throw，你精心設計的錯誤訊息管線靜靜地變成空轉，使用者永遠只看到「請求失敗（HTTP 401）」。

一律使用物件多載：new StatusError(401, { error: '...' })。官方文件在這一點與實作不符，以實作為準。

📄 Grocify/src/lib/server/auth.ts　★ 伺服器專用 ★

import { verifyToken } from '@clerk/backend';
import { StatusError } from 'expo-server';

/**
 * 每支路由的第一行都會呼叫它。
 *
 * 流程：Authorization: Bearer <jwt>
 *      → @clerk/backend 的 verifyToken()
 *      → payload.sub 就是 Clerk user id。
 *
 * ★ verifyToken 的型別是 (token, options) => Promise<JwtPayload>：
 *   成功 resolve payload、失敗 throw。
 *   沒有 { data, errors } tuple —— Clerk 官網某些頁面還印著那個舊形狀，
 *   照抄的話 `const { data } = await verifyToken(...)` 只會拿到 undefined。
 */
function getBearerToken(request: Request): string | null {
  const header = request.headers.get('authorization');
  if (!header) return null;

  const [scheme, token] = header.split(' ');
  if (!token || scheme.toLowerCase() !== 'bearer') return null;

  return token.trim();
}

export async function requireUserId(request: Request): Promise<string> {
  const token = getBearerToken(request);
  if (!token) {
    throw new StatusError(401, { error: '缺少 Authorization: Bearer <token> 標頭' });
  }

  const secretKey = process.env.CLERK_SECRET_KEY;
  if (!secretKey) {
    // 設定漏了就大聲 500，不要靜靜地放行。
    throw new StatusError(500, { error: '伺服器設定錯誤：CLERK_SECRET_KEY 未設定' });
  }

  let payload: Awaited<ReturnType<typeof verifyToken>>;
  try {
    payload = await verifyToken(token, { secretKey });
  } catch {
    throw new StatusError(401, { error: 'Session token 無效或已過期' });
  }

  const userId = payload.sub;
  if (!userId) {
    throw new StatusError(401, { error: 'Session token 沒有 sub claim' });
  }

  return userId;
}

/**
 * ★ 為什麼不設 authorizedParties？
 *   Clerk 只在「瀏覽器發出的 token」上放 azp claim；原生 App 的 token 沒有 origin。
 *   純原生的 API 設了它，會讓每一個請求都 401。
 *   若你也從 web build 打這支 API，才傳：
 *     authorizedParties: ['https://grocify.expo.app', 'http://localhost:8081']

  let body: unknown;
  try {
    body = await request.json();
  } catch {
    throw new StatusError(400, { error: 'Request body 必須是合法 JSON' });
  }

  // ★★★ 絕對不要把 { ...body } 直接丟給 Drizzle ★★★

  return Response.json(created, { status: 201 });

import { StatusError } from 'expo-server';
import { z } from 'zod';

import { deleteItem, updateItem } from '@/db/queries';
import { updateItemSchema } from '@/db/schema';
import { requireUserId } from '@/lib/server/auth';

// Zod 4 的頂層寫法；舊的 z.string().uuid() 在 v4 已 deprecated。
const idSchema = z.uuid();

/**
 * ★ items.id 是 uuid 欄位：任何非 UUID 的路徑片段（/api/items/abc、爬蟲、過期 id）
 *   丟進 eq(items.id, id) 會讓 Postgres 擲出 22P02 invalid input syntax for type uuid，
 *   變成一個沒人接的 500。先擋成 400。
 */
function invalidId(id: string): boolean {
  return !idSchema.safeParse(id).success;
}

/**
 * ★ 動詞是 PATCH，不是 PUT ★
 *   用戶端的 groceryApi.update() 送的是 PATCH。
 *   這裡若只匯出 PUT，Expo Router 會自動回 405，
 *   而錯誤訊息是「請求失敗（HTTP 405）」—— 完全看不出是動詞問題。
 */
export async function PATCH(
  request: Request,
  { id }: Record<'id', string>,
): Promise<Response> {
  const userId = await requireUserId(request);

  if (invalidId(id)) throw new StatusError(400, { error: 'Invalid id' });

  let body: unknown;
  try {
    body = await request.json();
  } catch {
    throw new StatusError(400, { error: 'Request body 必須是合法 JSON' });
  }

  // updateItemSchema 已用 .refine 擋掉空 patch（{} → 400，而不是 drizzle 的 500）
  const parsed = updateItemSchema.safeParse(body);
  if (!parsed.success) {
    return Response.json(
      { error: 'Invalid body', issues: parsed.error.issues },
      { status: 400 },
    );
  }

  const item = await updateItem(userId, id, parsed.data);

  // ★ 別人的項目也回 404（不是 403）。
  //   回 403 等於告訴攻擊者「這個 id 存在，只是不是你的」。
  if (!item) throw new StatusError(404, { error: '找不到項目' });

  return Response.json(item);
}

/** DELETE /api/items/:id → 204（無 body） */
export async function DELETE(
  request: Request,
  { id }: Record<'id', string>,
): Promise<Response> {
  const userId = await requireUserId(request);

  if (invalidId(id)) throw new StatusError(400, { error: 'Invalid id' });

  const deleted = await deleteItem(userId, id);
  if (!deleted) throw new StatusError(404, { error: '找不到項目' });

  return new Response(null, { status: 204 }); // 204 不能有 body
}

用戶端：那個「上架後才炸」的網址問題

💣 fetch('/api/items') 在 native 上是「魔法」，而魔法會在正式版消失

@expo/metro-runtime（expo-router 會拉進來）偷偷 patch 了 global.fetch：只要參數是以 / 開頭的字串，它就補上 window.location.origin。開發時那個 origin 是 Metro dev server；release build 裡 window.location 根本沒被安裝，於是 new URL('/api/items', undefined) 直接丟 TypeError: Invalid URL。

也就是說：相對路徑 fetch 在開發時「魔法般地會動」，上架後靜靜地爆炸。而且它只重寫 / 開頭的字串——fetch('api/items')（少一個斜線）永遠不會被重寫。本文一律自己組絕對網址，不依賴這個 polyfill。

import Constants from 'expo-constants';
import { Platform } from 'react-native';

function stripTrailingSlash(url: string): string {
  return url.replace(/\/+$/, '');
}

/**
 * 回傳 origin：
 *   dev 實機       → "http://192.168.1.20:8081"
 *   Android 模擬器 → "http://10.0.2.2:8081"
 *   tunnel         → "https://xxxx.exp.direct"
 *   正式版         → "https://grocify.expo.app"
 *   web            → ""（瀏覽器自己解析相對路徑）
 */
export function getApiBaseUrl(): string {
  // 1) 明確指定永遠優先。Metro 在打包時把值內嵌進 bundle。
  const explicit = process.env.EXPO_PUBLIC_API_URL;
  if (explicit) return stripTrailingSlash(explicit);

  // 2) Web：同源，相對路徑就好。
  if (Platform.OS === 'web') return '';

  // 3) Native + dev：打 Metro dev server（API routes 就跑在它上面）。
  //    hostUri 可能是：
  //      "192.168.1.20:8081"             → LAN（實機）
  //      "localhost:8081"                → 模擬器
  //      "abc-anonymous-8081.exp.direct" → tunnel（HTTPS，而且沒有 port）
  const hostUri = Constants.expoConfig?.hostUri;
  if (__DEV__ && hostUri) {
    const host = hostUri.split(':')[0];

    // ★ tunnel 是 HTTPS-only。寫死 http:// 會在「實機 + tunnel」
    //   這個最常見的遠端測試組合上整批失敗。
    if (/\.exp\.direct$/.test(host)) return `https://${hostUri}`;

    // ★ Android 模擬器裡的 "localhost" 指的是「模擬器自己」，不是你的電腦。
    //   10.0.2.2 是 Android 模擬器對應到宿主機 loopback 的特殊位址。
    //   （iOS 模擬器與電腦共用 loopback，localhost 是對的，不用改。）
    if (Platform.OS === 'android' && (host === 'localhost' || host === '127.0.0.1')) {
      return `http://${hostUri.replace(host, '10.0.2.2')}`;
    }

    return `http://${hostUri}`;
  }

  // 4) Native + production 卻沒設 EXPO_PUBLIC_API_URL → 明確炸掉，
  //    不要靜靜地打到一個不存在的網址。
  throw new Error(
    '找不到 API origin。請在 EAS 的 preview / production 環境設定 EXPO_PUBLIC_API_URL' +
      '（例如 https://grocify.expo.app），然後重新 build。',
  );
}

/** 把 "/api/items" 變成 iOS / Android / web 都能用的絕對網址。 */
export function apiUrl(path: string): string {
  const base = getApiBaseUrl();
  return `${base}${path.startsWith('/') ? path : `/${path}`}`;
}

export class ApiError extends Error {
  readonly status: number;
  constructor(status: number, message: string) {
    super(message);
    this.name = 'ApiError';
    this.status = status;
  }

async function request<T>(path: string, init: RequestInit = {}): Promise<T> {
  // 每一發 request 都重拿一次 token（getToken() 內部會自動 refresh）。
  const token = await getAuthToken();

  // ★ 用 Headers 而不是物件展開 ★
  // init.headers 的型別是 HeadersInit，可能是 Headers 實例或 [k, v][]。
  // 對 Headers 做 { ...init.headers } 會得到 {}，呼叫端傳的標頭會被靜靜吃掉。
  const headers = new Headers(init.headers);
  headers.set('Content-Type', 'application/json');
  if (token) headers.set('Authorization', `Bearer ${token}`);

  const res = await fetch(apiUrl(path), { ...init, headers });

  if (!res.ok) {
    let message = `請求失敗（HTTP ${res.status}）`;
    try {
      // 伺服器端的 StatusError 一律傳「物件」，所以這裡一定拿得到 { error: "..." }。
      const body = (await res.json()) as { error?: string };
      if (body?.error) message = body.error;
    } catch {
      // 框架自動產生的 405 / 500 頁面不是 JSON，維持預設訊息。
    }
    throw new ApiError(res.status, message);
  }

  if (res.status === 204) return undefined as T;
  return (await res.json()) as T;
}

        // 因為 store 設了 skipHydration，「第一次讀磁碟」就發生在這裡 ——
        // 而且是在我們已經知道使用者是誰之後。
        useGroceryStore.persist.setOptions({ name: keyFor(userId) });
        await useGroceryStore.persist.rehydrate();
        // ★ 注意：這裡不呼叫 fetchItems()。
        //   抓資料的主人只有一個 —— 清單畫面。
        if (cancelled) return;
      } else {
        // ── 登出。順序很重要，因為 persist 會在「每一次 set()」時寫回磁碟 ──
        // 1) 先把 persist 的目標 key 切走 → 之後任何 set() 都打不到這位使用者的 key
        const previousKey = useGroceryStore.persist.getOptions().name ?? PLACEHOLDER_KEY;
        useGroceryStore.persist.setOptions({ name: PLACEHOLDER_KEY });
        // 2) 清記憶體
        useGroceryStore.getState().reset();
        useGroceryStore.getState().setHasHydrated(true); // 沒登入 → 沒東西可 hydrate
        // 3) 真的把離線快取刪掉（要 await，不能 fire-and-forget）
        await AsyncStorage.multiRemove([previousKey, PLACEHOLDER_KEY]);
      }
    })();

    return () => { cancelled = true; };
  }, [isLoaded, isSignedIn, userId]);

  return null;
}

💣 登出順序寫反 = 資安事故

直覺會想寫「先 clearStorage() 再 reset()」。那是錯的：persist 會在每一次 set() 時寫回磁碟，所以 reset() 的那個 set() 馬上又把空狀態寫回上一位使用者的 key。正確順序是：先把 key 切成佔位值（之後所有寫入都打不到使用者的 key）→ reset() → await AsyncStorage.multiRemove()。

AsyncStorage 是全裝置共用、而且未加密。不把 key 依 userId 切開、登出不清，下一個在這台手機登入的人就會讀出前一個人的購物清單。

import AsyncStorage from '@react-native-async-storage/async-storage';
import { create } from 'zustand'; // ★ v5 已移除 default export，必須具名匯入
import { createJSONStorage, persist } from 'zustand/middleware';

import { groceryApi } from '@/lib/api';
import type { GroceryItem, NewGroceryItem } from '@/types/grocery';

export type GroceryStatus = 'idle' | 'loading' | 'refreshing' | 'error';

interface GroceryState {
  items: GroceryItem[];
  status: GroceryStatus;
  error: string | null;
  /** 飛行中的樂觀新增（temp id）；用來把那一列 disable 掉。 */
  pendingIds: string[];
  /** AsyncStorage 的 rehydrate 是非同步的：第一幀 items 一定是 []。 */
  hasHydrated: boolean;

  setHasHydrated: (v: boolean) => void;
  fetchItems: (opts?: { refresh?: boolean }) => Promise<void>;
  addItem: (input: NewGroceryItem) => Promise<void>;
  toggleItem: (id: string) => Promise<void>;
  updateQuantity: (id: string, quantity: number) => Promise<void>;
  deleteItem: (id: string) => Promise<void>;
  clearCompleted: () => Promise<void>;
  reset: () => void;
}

type PersistedGroceryState = Pick<GroceryState, 'items'>;

const nowIso = () => new Date().toISOString();
const toMessage = (e: unknown) => (e instanceof Error ? e.message : '發生未知錯誤');
const isTemp = (id: string) => id.startsWith('temp-');
const makeTempId = () => `temp-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`;

// ★ 注意 curried 形式：create<GroceryState>()( ... ) ★
// zustand v5 的 Create 型別只有兩個 overload，TypeScript 無法「部分推導」泛型，
// 所以只要用了 middleware，就必須寫成 create<T>()(persist(...))。
// 那個空的 () 不是 typo。
export const useGroceryStore = create<GroceryState>()(
  persist(
    (set, get) => ({
      items: [],
      status: 'idle',
      error: null,
      pendingIds: [],
      hasHydrated: false,

      setHasHydrated: (v) => set({ hasHydrated: v }),

      fetchItems: async ({ refresh = false } = {}) => {
        set({ status: refresh ? 'refreshing' : 'loading', error: null });
        try {
          const items = await groceryApi.list();
          set({ items, status: 'idle', error: null });
        } catch (e) {
          // ★ 刻意不清空 items：離線時使用者還是看得到 rehydrate 出來的清單。
          set({ status: 'error', error: toMessage(e) });
        }
      },

      /* ── 樂觀新增：先畫出來，伺服器回來後把 temp 列換成真正的列 ── */
      addItem: async (input) => {
        const tempId = makeTempId();
        const optimistic: GroceryItem = {
          id: tempId,
          name: input.name,
          quantity: input.quantity ?? 1,
          unit: input.unit ?? '個',
          category: input.category ?? 'other',
          completed: false,
          createdAt: nowIso(),
          updatedAt: nowIso(),
        };

        set((s) => ({
          items: [optimistic, ...s.items],
          pendingIds: [...s.pendingIds, tempId],
          error: null,
        }));

        try {
          const saved = await groceryApi.create(input);
          set((s) => ({ items: s.items.map((i) => (i.id === tempId ? saved : i)) }));
        } catch (e) {
          // ★★★ 只回滾「我動過的那一列」，不要整包蓋回快照 ★★★
          //     否則會把 request 飛行期間使用者做的其他修改一起吃掉。
          set((s) => ({
            items: s.items.filter((i) => i.id !== tempId),
            error: toMessage(e),
          }));
        } finally {
          set((s) => ({ pendingIds: s.pendingIds.filter((id) => id !== tempId) }));
        }
      },

      /* ── 會「秒回」的勾選：UI 同一幀翻面，網路之後才發生 ── */
      toggleItem: async (id) => {
        const target = get().items.find((i) => i.id === id);
        if (!target) return;
        // 還在新增中的列沒有真 id，PATCH 會 404。UI 端已用 pendingIds 把它 disable 掉。
        if (isTemp(target.id)) return;

        const next = !target.completed;
        set((s) => ({
          items: s.items.map((i) =>
            i.id === id ? { ...i, completed: next, updatedAt: nowIso() } : i,
          ),
          error: null,
        }));

        try {
          const saved = await groceryApi.update(id, { completed: next });
          set((s) => ({ items: s.items.map((i) => (i.id === id ? saved : i)) }));
        } catch (e) {
          // 只把「這一列」換回動作前的樣子（target 是 await 之前抓到的舊列）。
          set((s) => ({
            items: s.items.map((i) => (i.id === id ? target : i)),
            error: toMessage(e),
          }));
        }
      },

      updateQuantity: async (id, quantity) => {
        if (quantity < 1) return;
        const target = get().items.find((i) => i.id === id);
        if (!target || isTemp(target.id)) return;

        set((s) => ({
          items: s.items.map((i) =>
            i.id === id ? { ...i, quantity, updatedAt: nowIso() } : i,
          ),
          error: null,
        }));

        try {
          const saved = await groceryApi.update(id, { quantity });
          set((s) => ({ items: s.items.map((i) => (i.id === id ? saved : i)) }));
        } catch (e) {
          set((s) => ({
            items: s.items.map((i) => (i.id === id ? target : i)),
            error: toMessage(e),
          }));
        }
      },

      deleteItem: async (id) => {
        const before = get().items;
        const index = before.findIndex((i) => i.id === id);
        if (index < 0) return;
        const removed = before[index];
        if (isTemp(removed.id)) return;

        set((s) => ({ items: s.items.filter((i) => i.id !== id), error: null }));

        try {
          await groceryApi.remove(id);
        } catch (e) {
          // 把那一列插回「原本的位置」；其他列在飛行期間的變動一律保留。
          set((s) => {
            const items = [...s.items];
            items.splice(Math.min(index, items.length), 0, removed);
            return { items, error: toMessage(e) };
          });
        }
      },

      clearCompleted: async () => {
        const removed = get().items
          .map((item, index) => ({ item, index }))
          .filter(({ item }) => item.completed && !isTemp(item.id));
        if (removed.length === 0) return;

        const removedIds = new Set(removed.map(({ item }) => item.id));
        set((s) => ({ items: s.items.filter((i) => !removedIds.has(i.id)), error: null }));

        try {
          await groceryApi.clearCompleted();
        } catch (e) {
          // 依原本的 index 插回去，不要一股腦推到清單最後面。
          set((s) => {
            const items = [...s.items];
            for (const { item, index } of removed) {
              items.splice(Math.min(index, items.length), 0, item);
            }
            return { items, error: toMessage(e) };
          });
        }
      },

      reset: () =>
        set({ items: [], status: 'idle', error: null, pendingIds: [], hasHydrated: false }),
    }),
    {
      // 這只是佔位值：真正的 key 由 <ClerkTokenBridge /> 換成 grocify-list-<userId>。
      name: 'grocify-list',
      version: 1,
      // ★ 關鍵：在「還不知道是誰登入」的時候，不要急著 hydrate。
      //   預設的 persist 會在「模組被 import 的那一刻」就開始讀磁碟，
      //   而那時 Clerk 還沒解出 session、key 還是佔位值 —— 讀到的必然是空的，
      //   然後 hasHydrated 變成 true，這個旗標就白做了。
      skipHydration: true,
      storage: createJSONStorage<PersistedGroceryState>(() => AsyncStorage),
      // 絕不持久化 status / error / pendingIds，否則會開機直接卡在 spinner。
      // 也把 temp- 列濾掉：一個「新增到一半就被殺掉」的 App，
      // 不該留下永遠點不動的幽靈列。
      partialize: (state): PersistedGroceryState => ({
        items: state.items.filter((i) => !isTemp(i.id)),
      }),
      // ★ 自訂 merge：rehydrate 時「以磁碟為準」。
      //   zustand 預設的 merge 是 { ...current, ...persisted }：
      //   當使用者 B 沒有快取時 persisted 是 undefined
      //   → 記憶體裡使用者 A 的 items 會被原封不動保留，並且寫進 B 的 key。
      merge: (persisted, current): GroceryState => ({
        ...current,
        items: (persisted as PersistedGroceryState | undefined)?.items ?? [],
      }),
      onRehydrateStorage: () => (state, error) => {
        if (error) console.warn('[grocify] rehydrate 失敗', error);
        state?.setHasHydrated(true);
      },
    },
  ),
);

import { useMemo } from 'react';
import { useShallow } from 'zustand/react/shallow';

import type { Category, GroceryItem } from '@/types/grocery';
import { useGroceryStore } from './useGroceryStore';

/* ── 1. 回傳純量／穩定參考的 selector —— 不需要任何 equality function ── */
export const useItems = () => useGroceryStore((s) => s.items);
export const useStatus = () => useGroceryStore((s) => s.status);
export const useIsRefreshing = () => useGroceryStore((s) => s.status === 'refreshing');
export const useError = () => useGroceryStore((s) => s.error);
export const useHasHydrated = () => useGroceryStore((s) => s.hasHydrated);

/** 某一列是不是「正在新增中」—— 每列各自訂閱一個 boolean，翻面時只有那一列重繪。 */
export const useIsPending = (id: string) =>
  useGroceryStore((s) => s.pendingIds.includes(id));

/* 衍生值一律「在 selector 裡算」，不進 store。
   一旦入庫，你就得在六個 action 裡各自記得同步它，
   遲早忘掉一個，然後畫面就開始說謊。 */
export const useTotalCount = () => useGroceryStore((s) => s.items.length);

/* ── 2. 回傳「物件字面量」的 selector → 一定要包 useShallow ──
 *
 * v5 的預設比較是 Object.is（對齊 React 的 useSyncExternalStore）。
 * 沒包 useShallow 的話，每次 store 變動都會產生一個新的 {}，
 * 元件無限重繪，甚至會噴 React 的
 * "The result of getSnapshot should be cached to avoid an infinite loop"。
 */
export function useGroceryStats(): { total: number; completed: number; remaining: number } {
  return useGroceryStore(
    useShallow((s) => {
      const total = s.items.length;
      const completed = s.items.reduce((n, i) => n + (i.completed ? 1 : 0), 0);
      return { total, completed, remaining: total - completed };
    }),
  );
}

/** action 的參考永遠不變，所以整包抓出來是安全的。 */
export const useGroceryActions = () =>
  useGroceryStore(
    useShallow((s) => ({
      fetchItems: s.fetchItems,
      addItem: s.addItem,
      toggleItem: s.toggleItem,
      updateQuantity: s.updateQuantity,
      deleteItem: s.deleteItem,
      clearCompleted: s.clearCompleted,
    })),
  );

/* ── 3. 分組（group by）→ useShallow 救不了你 ──
 *
 * shallow 只比一層，而每次呼叫產生的「內層陣列」都是新物件，
 * 第一層的元素參考就變了 → 照樣判定為不同 → 照樣重繪。
 * 正解：選出穩定的 items 參考，然後在 useMemo 裡分組。
 */
export type CategorySection = { title: Category; data: GroceryItem[] };

export function useItemsByCategory(): CategorySection[] {
  const items = useGroceryStore((s) => s.items); // 這個參考只有在 items 真的換了才變
  return useMemo(() => {
    const map = new Map<Category, GroceryItem[]>();
    for (const item of items) {
      const bucket = map.get(item.category);
      if (bucket) bucket.push(item);
      else map.set(item.category, [item]);
    }
    return [...map.entries()].map(([title, data]) => ({ title, data }));
  }, [items]);
}

💣 Zustand 的四個經典死法

  1. const store = useGroceryStore()（不給 selector）= 訂閱整個 store。勾一個核取方塊會重繪標題、按鈕、每一列。永遠選最窄的東西。
  2. selector 回傳新物件／新陣列 → 無限重繪。物件字面量用 useShallow；巢狀結構（group-by）連 useShallow 都救不了（它只比一層，而內層陣列每次都是新的）。
  3. create<T>(persist(...)) 少了那對空括號 → 型別炸開。必須 create<T>()(persist(...))。
  4. v4 的 useStore(selector, shallow) 在 v5 不再編譯。改用 useStore(useShallow(selector))。

誠實的分界線：items 其實是伺服器狀態

這個 store 是很好的教材——它把「樂觀更新／回滾／離線快取」的機械原理攤在眼前。但必須把話講清楚，而不是假裝它就是最終架構：

判準只有一句：問「這份資料的真相在誰身上？」如果答案是資料庫，它就是伺服器狀態，你放進 Zustand 的那份只是「一份會過期的影本」。

Grocify 的 items 住在 Neon、別台裝置會改它、它會過期——它就是伺服器狀態。上面 store 裡繞著它做的每一件事（狀態機、錯誤、下拉重抓、樂觀回滾、離線快取），都是在手刻一個功能比較差的 TanStack Query：

能力Zustand storeTanStack Query
請求去重（兩個畫面同時掛載 → 兩發 GET）要自己做內建
stale-while-revalidate無內建
回到前景／網路恢復時背景重抓無內建（RN 要先接 focusManager／onlineManager）

正式產品的切法：items 用 TanStack Query，UI 狀態用 Zustand。兩條路只能選一條——同時用兩者管 items，就有兩個真相來源，兩邊的樂觀更新互相蓋，會除錯到天亮。TanStack Query 的等價實作：

import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { groceryApi } from '@/lib/api';
import type { GroceryItem } from '@/types/grocery';

export const groceryKeys = {
  all: ['groceries'] as const,
  list: () => [...groceryKeys.all, 'list'] as const,
};

export function useItemsQuery() {
  return useQuery({ queryKey: groceryKeys.list(), queryFn: groceryApi.list });
}

/** onMutate / onError / onSettled 就是我們手刻的「快照 + 回滾」。 */
export function useToggleItem() {
  const qc = useQueryClient();

  return useMutation({
    mutationFn: ({ id, completed }: { id: string; completed: boolean }) =>
      groceryApi.update(id, { completed }),

    onMutate: async ({ id, completed }) => {
      await qc.cancelQueries({ queryKey: groceryKeys.list() });
      const previous = qc.getQueryData<GroceryItem[]>(groceryKeys.list());
      qc.setQueryData<GroceryItem[]>(groceryKeys.list(), (old) =>
        (old ?? []).map((i) => (i.id === id ? { ...i, completed } : i)),
      );
      return { previous };
    },

    onError: (_err, _vars, ctx) => {
      if (ctx?.previous) qc.setQueryData(groceryKeys.list(), ctx.previous);
    },

    onSettled: () => {
      void qc.invalidateQueries({ queryKey: groceryKeys.list() });
    },
  });
}

⚠️ React Native 專屬的兩個必做設定（純網頁教學不會提，但手機上不做就會「怎麼都不重抓」）：RN 沒有 navigator.onLine，也沒有 window focus 事件。必須用 AppState 餵 focusManager、用 NetInfo 餵 onlineManager，否則 refetchOnWindowFocus 與 refetchOnReconnect 永遠不會觸發——而且不會有任何錯誤訊息。另外 TanStack v5 把 status 'loading' 改名成 'pending'。

證明回滾不會吃掉其他修改：斷網後先「新增一項」，趁 POST 還在飛時去勾另一列新增的那列消失（回滾），但你剛勾的那一列仍然是勾起來的。若用整包快照回滾，那個勾選會一起被抹掉。
證明離線快取：登入後載入清單 → 強制關閉 → 開飛航模式 → 重開 App清單立刻從 AsyncStorage 畫出來，fetchItems 失敗、紅字出現，但列還在。而且不會先閃一下「清單是空的」——因為畫面是 gate 在 hasHydrated，不是 items.length === 0。
證明使用者隔離：A 登入建幾筆 → 登出 → B 登入B 看到空清單，絕不會看到 A 的東西。AsyncStorage.getAllKeys() 裡不該再有 grocify-list-<A 的 userId>。
證明沒有重複請求：在 groceryApi.list() 裡 log 一行，冷啟動一次只印一次。若印兩次，代表 bridge 又偷偷呼叫 fetchItems() 了——抓資料的主人只能有一個。

  useEffect(() => {

  const handleToggle = useCallback((id: string) => void toggleItem(id), [toggleItem]);

          accessibilityLabel={`共 ${total} 項，已完成 ${completed} 項，還剩 ${remaining} 項`}

        getItemLayout={(_, index) => ({ length: ITEM_SIZE, offset: ITEM_SIZE * index, index })}

npx expo install expo-blur expo-glass-effect

💣 千萬不要把 expo-blur / expo-glass-effect 寫進 app.json 的 plugins。它們沒有 config plugin（tarball 裡根本沒有 app.plugin.js）。寫上去，npx expo run:ios 會在解析設定的階段就死於 PluginError: Failed to resolve plugin for module "expo-blur"——Xcode 都還沒被叫起來。它們是自動連結模組，只要安裝、不要註冊。很多部落格在這裡教錯。

import { BlurView } from 'expo-blur';
import { GlassView, isLiquidGlassAvailable } from 'expo-glass-effect';
import { Platform, StyleSheet, View, useColorScheme } from 'react-native';

/**
 * 分頁列的玻璃底。三層降級：
 *   1. iOS 26+   → expo-glass-effect 的 <GlassView>（真正的液態玻璃）
 *   2. iOS 15~18 → expo-blur 的 <BlurView>（毛玻璃）
 *   3. Android   → 半透明色塊（即時模糊很吃效能，預設關掉）
 *
 * ★ isLiquidGlassAvailable() 是「執行期」檢查，不是編譯期常數：
 *   只有「用 Xcode 26 編出來」且「跑在 iOS 26」時才會是 true。
 *
 * ★ 在 iOS 25 以下，<GlassView> 不報錯也不模糊 ——
 *   它會靜默變成一個透明 View。所以一定要先判斷再決定 render 哪一個，
 *   否則你會得到一條「什麼都沒有」的分頁列。
 */
export default function GlassTabBarBackground() {
  const scheme = useColorScheme();

  if (Platform.OS === 'ios' && isLiquidGlassAvailable()) {
    return (
      <GlassView
        style={StyleSheet.absoluteFill}
        glassEffectStyle="regular" // 'clear' | 'regular' | 'none'
        colorScheme="auto"
      />
    );
  }

  if (Platform.OS === 'ios') {
    return (
      <BlurView
        style={StyleSheet.absoluteFill}
        intensity={80}
        tint={scheme === 'dark' ? 'systemChromeMaterialDark' : 'systemChromeMaterialLight'}
      />
    );
  }

  // Android：想要真模糊，換成
  //   <BlurView intensity={60} experimentalBlurMethod="dimezisBlurView" ... />
  // ★ SDK 54 的 prop 名稱是 experimentalBlurMethod，不是新版文件的 blurMethod。
  return (
    <View
      style={[
        StyleSheet.absoluteFill,
        {
          backgroundColor:
            scheme === 'dark' ? 'rgba(17,17,17,0.94)' : 'rgba(255,255,255,0.94)',
        },
      ]}
    />
  );
}

⚠️ 浮動分頁列會蓋住最後一筆項目。tabBarStyle.position: 'absolute' 之後，清單底部一定要留空間。用 useBottomTabBarHeight()（從 @react-navigation/bottom-tabs 匯入，不要自己安裝這個套件——expo-router 已經相依它，多裝一份會產生第二個 React context，然後這個 hook 會 throw）補上 paddingBottom，或者像本文清單頁那樣直接用 pb-24。

💣 切到原生分頁時，畫面必須跟著改的兩件事

1. 移除 useBottomTabBarHeight()。原生分頁列底下沒有那個 context，呼叫會直接 throw Couldn't find the bottom tab bar height。iOS 由 UIKit 自己算內容邊距，保留 contentInsetAdjustmentBehavior="automatic" 即可。

2. 要看到膠囊動畫，清單必須是原生 ScrollView。官方文件明載：原生分頁與 FlatList 的整合有限，「捲動時縮小」與「點分頁列回頂端」都不會生效——那不是你的 bug。

還有一個「替代版本檔案放哪裡」的坑，很多人踩：

⚠️ 不要把 _layout.classic.tsx 這種替代版放在 src/app/(home)/ 裡。expo-router 把檔名去副檔名後只取第一段，所以 _layout.classic.tsx 與 _layout.tsx 會被認成同一個路由的 layout，開發模式直接丟 layout conflict，正式版則是隨機挑一個先找到的用（更難查）。替代版一律放在路由根目錄之外，需要時把「內容」複製進去。

import { useUser } from '@clerk/expo';
import * as Sentry from '@sentry/react-native';
import { useEffect } from 'react';

/**
 * 把 Clerk 的登入使用者同步到 Sentry scope。
 *
 * ⚠️ 這個 hook 必須在「根部」呼叫（<SentryUserSync />），不要只在洞察畫面呼叫。
 *    只在洞察畫面呼叫的話，使用者沒進過那一頁之前，
 *    所有崩潰（登入頁、清單頁、規劃頁 —— 也就是 App 的大部分）
 *    都不會帶使用者資訊。
 */
export function useSentryUser(): void {
  const { isLoaded, isSignedIn, user } = useUser();

  useEffect(() => {
    if (!isLoaded) return;

    if (!isSignedIn || !user) {
      Sentry.setUser(null); // 登出後清空，避免把後續事件掛在前一個使用者身上
      return;
    }

    Sentry.setUser({
      id: user.id,
      email: user.primaryEmailAddress?.emailAddress,
      username: user.fullName ?? user.username ?? undefined,
    });
  }, [isLoaded, isSignedIn, user]);
}

🔴 EAS Hosting 讀不到 secret 可見度的變數

這是「App + API Routes 同一個專案」這種架構下最容易撞死的一條，而且極度反直覺。把 DATABASE_URL 建成 --visibility secret（最「安全」的直覺選擇）會讓部署後的 API Route 拿到 undefined：eas deploy 會成功、伺服器會正常啟動、然後每一個 API 請求都 500。

必須是 sensitive。secret 是給 build worker 用的（例如私有 npm token）。而且 sensitive 已經足夠安全——這些值從頭到尾沒有進過 App bundle。真正的安全邊界是「不加 EXPO_PUBLIC_ 前綴」，不是 EAS 的可見度標籤。

✅ eas update 就能送達❌ 必須重新 eas build 並重新送審
JavaScript／TypeScript 程式碼（畫面、hooks、store）原生程式碼、新增原生相依套件

runtimeVersion: appVersion 的雙面刃：改了 app.json 的 version（1.0.0 → 1.0.1）就等於宣告了一個新的執行環境，先前發出去的 binary 收不到這個 OTA——而且不會有任何錯誤，它只是安靜地繼續跑舊版。純 JavaScript 的緊急修補想推給既有使用者：不要動 version，只推 eas update。

channel 與 branch 不是同義詞：channel 綁在 binary 上（打包時決定，之後改不了）；branch 是 update 的容器。channel → branch 是可以在後台重新對應的映射——這正是「把 production channel 指回舊 branch 就能瞬間回滾」的機制。
