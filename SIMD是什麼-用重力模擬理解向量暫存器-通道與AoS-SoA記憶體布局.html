Single Instruction · Multiple Data

一條指令
同時算完八組資料

電腦真正的瓶頸很少是「算得不夠快」，而是「資料擺錯位置」。這份互動教材以一個最笨的 O(N²) 重力模擬為起點，拆解單指令多資料（Single Instruction Multiple Data，SIMD）如何在不新增執行緒、不增加核心的前提下把同樣的工作做得更快，以及為什麼真正困難的部分從來都不是指令本身。

核心洞見
  • 01 向量暫存器不是拿來裝「一個超大的數」，而是把同樣的位元寬度切成多個獨立的通道，讓一條指令同時作用在每個通道上。
  • 02 暫存器名稱決定總位元寬，指令後綴決定每個元素多寬；兩者相除就是通道數。這也是為什麼有些運算組合根本不存在對應指令。
  • 03 SIMD 的限制不是「只能做一種運算」，而是同一條指令在所有通道上必須做同一件事；容許逐通道指定運算會讓指令編碼與解碼邏輯直接爆炸。
  • 04 真正的工程難點在資料布局。把結構陣列改寫成陣列結構，看起來反直覺，卻同時解決了向量載入與快取行浪費兩個問題。
  • 05 SIMD 與多執行緒不是互相取代的關係。每個核心都有自己的向量執行資源，兩層平行度可以疊加，但要同時吃滿兩層，演算法設計的難度會再上一階。

01

O(N²) 的重力沙盒

這個模擬只做一件事：把一團粒子丟進畫面，讓重力決定它們怎麼走。演算法選的是最直白也最浪費的版本 ——每一顆粒子都去考慮系統中其他所有粒子的影響。粒子數一旦往上加，畫面就開始卡，因為工作量是 平方成長的。先把滑桿拉到 400 以上，再切換下方的運算模式，觀察每步耗時的變化。

02

一對粒子，六次算術

重力由質量產生。取兩顆粒子 i 與 j，依牛頓萬有引力定律，兩者之間吸引力的大小與質量乘積成正比、與距離平方成反比：

$$F = G\,\frac{m_i m_j}{r^{2}}$$

模擬真正關心的不是力，而是位置怎麼變。由牛頓第二運動定律 \(F = m a\)，把兩式合併後，j 對 i 產生的加速度只跟 j 的質量有關：

$$a_{i} = G\,\frac{m_j}{r^{2}}$$

因為是二維空間，加速度是向量，有水平與垂直兩個分量。系統中每一顆其他粒子都以不同大小、不同方向拉扯著它，而粒子無法同時往所有方向去；所幸加速度可以疊加，把所有向量相加就得到淨加速度：

$$\vec{a}_{i} = G \sum_{j \neq i} m_j\,\frac{\vec{r}_{ij}}{\lVert \vec{r}_{ij} \rVert^{3}}$$

算出淨加速度後，用一個很小的時間步長更新速度、再更新位置，畫面就知道該把粒子畫在哪裡。位置一變，距離跟著變，先前算出的加速度立刻作廢，整套流程必須從頭再跑一次——而且要快到讓人眼看起來是連續運動。

    03

    向量暫存器與通道

    處理器做算術時，靠的是一組通用暫存器，寬度通常和架構相關：32 位元系統配 32 位元暫存器，也因此無法在單一基本運算裡處理 64 位元的數，只能拆成好幾步。 現代處理器另外備有一種完全相反的東西——向量暫存器。它寬得多，但那些位元不是用來表示一個超大的數，而是切成多個獨立的通道，每個通道各放一個較小的數。 暫存器名稱決定總寬度，指令後綴決定每個元素多寬，兩者相除就是通道數：

    $$\text{lanes} = \frac{W_{\text{reg}}}{W_{\text{elem}}}$$

    後綴的意義

    整數運算以 B、W、D、Q 表示位元組、字組、雙字組、四字組；浮點則用 PS 表示單精度封裝、PD 表示倍精度封裝。前綴的 V 或 VP 代表這是向量封裝運算。

    缺席的乘法

    x86-64 沒有直接的封裝 8 位元整數乘法，因為兩個 8 位元整數相乘極易溢位。實務上會先擴寬成較大的元素，再以較寬的通道相乘。

    缺席的除法

    整數除法在硬體上既複雜又慢。為了餵飽多個通道而複製足夠的整數除法器，要耗掉可觀的矽面積，換來的卻是一個遠不如加減乘常見的運算，因此封裝除法只提供浮點版本。

    04

    為什麼一定是「單一」指令

    這裡有個常見誤解需要澄清：SIMD 並非只能做一種運算，不同運算當然可以一條接一條地執行。真正的限制是—— 同一條指令，在所有通道上做的必須是同一件事。 原因在指令編碼與控制邏輯的成本。告訴處理器「把這兩個數相加」很單純；告訴它「把這幾組數兩兩相加」也一樣單純； 但告訴它「第一個通道相加、第二個相乘、第三個相除、第四個相減」則是完全不同層級的問題。

    05

    記憶體布局：AoS 對上 SoA

    暫存器裡的資料得先從記憶體載入。向量暫存器有專屬的載入指令，一次可以搬進 256 個連續位元——前提是那些值真的緊鄰在一起。 如果它們散落各處，單次連續載入就無法一口氣取齊；只能改用多次載入加上重排，或者在支援的指令集上動用 gather。 這些做法都要付出額外成本，把原本想從平行算術裡賺到的時間又吐回去一部分。

    Array of Structures

    從程式設計的角度，這是最自然的寫法：一顆粒子是一個結構，裝著 x 位置、y 位置、x 速度、y 速度與質量；整個系統就是這種結構的陣列。屬於同一顆粒子的東西全部放在一起。

    struct Particle { float x, y, vx, vy, m; };
Particle p[N];   // x0 y0 vx0 vy0 m0 | x1 y1 ...
    Structure of Arrays

    解法有點彆扭：改成一個結構裝著五條陣列。同一顆粒子的屬性被拆散了，但同一種屬性、來自不同粒子的值變成連續排列——這正是向量載入與快取都想要的形狀。

    struct System {
  float x[N], y[N], vx[N], vy[N], m[N];
};               // x0 x1 x2 x3 x4 x5 x6 x7 ...
    快取行檢視器

    量測方式：兩種布局各先暖身兩輪，再交替執行五輪、每輪跑八趟後取平均，最後取五輪的最小值，以降低即時編譯與其他程序造成的干擾；執行期間會暫停上方的模擬，結束後緩衝區隨即釋放。 為什麼位元組流量差五倍，時間卻只差一點五倍？ 看上面兩張卡的有效頻寬就知道了：結構陣列那一側通常會跑到十幾 GB/s，已經逼近這台機器的記憶體頻寬上限，它確實是被頻寬卡住的； 陣列結構那一側卻只有幾 GB/s，離上限還很遠——它根本不是被記憶體卡住，而是被 JavaScript 那個一次只加一個數的純量迴圈卡住。 基準線本身沒有貼到天花板，比值自然拉不到五倍。要看到接近五倍的時間差，必須連迴圈的成本也一起壓下去，也就是用 SIMD 一次加八個。 這正好說明了布局與向量化是一組的：只改布局、不向量化，只能拿到其中一部分。

    實際數字因機器而異，取決於快取大小與記憶體頻寬——結構陣列那 20 MB 幾乎一定放不進最後一層快取，陣列結構的 4 MB 則多半放得進，差距正是從這裡來的。

    為什麼直覺會害了效能

    現代處理器極少只取回你要的那一個值，而是一次載入鄰近的一整塊記憶體，也就是一條快取行。用結構陣列時，這條快取行會連帶把用不到的 y 座標、速度與質量一起搬進來；於是每條快取行裡真正有用的值變少，處理器就得更頻繁地去記憶體搬新的快取行，只為了湊齊那些四散的 x 座標。 把布局換成陣列結構之後，同一條快取行裝的全都是 x 座標，而且它們連續，能夠直接以一次向量載入送進暫存器。 程式碼的組織直覺，和硬體的執行效率，在這裡是互相牴觸的。

    06

    兩層平行度可以疊加

    談 SIMD 時常被忽略的一點是：現代處理器不只有一個執行核心，而且每個核心都有自己的向量執行資源。 所以 SIMD 與多執行緒不是彼此競爭的兩種平行化手段，而是可以同時使用的兩個層級——不同執行緒在不同核心上跑，每個核心內部又同時處理多個通道。

    07

    難的從來不是指令

    SIMD 有個奇特之處：指令本身其實相當簡單直觀。難的是重新設計演算法與資料，好讓這些指令真的用得上。 有時候要動的是像「資料在記憶體裡怎麼排」這麼根本的東西；那些用一般寫法看起來再自然不過的演算法，可能得改寫成有點彆扭的形狀，好讓執行期需要一起處理的值，在記憶體裡也剛好放在一起。

    好消息是不一定得親手寫 SIMD。現代編譯器的最佳化技術相當擅長辨認可以向量化的常見模式，把原本一次處理一個值的純量指令，換成一次處理數個值的向量指令——這就是自動向量化。前提是最佳化選項有開，而且程式碼的結構讓向量化成為可能。

    回到沙盒：加速之後，互動仍然是用同樣的方式計算，複雜度依舊是 O(N²)。工作量一點都沒有減少，只是硬體被用得更充分。所以粒子數再往上推，向量化版本一樣會撐不住——真要突破，得換演算法，例如以樹狀結構近似遠處質量的方法。

    編譯器擅長辨認的形狀
    • 迴圈次數在進入前即可確定，且沒有提早跳出
    • 每次迭代之間沒有資料相依，順序可以任意調換
    • 以固定步長走訪連續記憶體，最好是步長為一
    • 指標之間不會互相重疊，編譯器才敢放心重排
    • 單純的歸約，例如把一整條陣列加總起來
    會讓向量化失敗的形狀
    • 迴圈內含函式呼叫或例外處理，無法內聯展開
    • 分散式讀寫，索引來自另一條陣列
    • 本次迭代要用到上一次的結果，形成鏈狀相依
    • 結構陣列造成的跨步存取，連續性被打斷
    08

    所以，該寫 AoS 還是 SoA

    短答案

    預設寫結構陣列。 等到某一段熱迴圈被實際量出來是瓶頸，而且它只碰結構裡少數幾個欄位、又要掃過大量元素時， 再只把那一段改成陣列結構。

    陣列結構不是比較好的寫法，而是比較專門的寫法。它用可讀性與維護成本，去換一個很具體的東西：讓連續向量載入成為可能。 如果那段程式碼從頭到尾沒打算向量化，也沒有大到會刷爆快取，這筆交易多半划不來——本頁的重力沙盒就是活生生的例子，改了布局卻沒有向量化，實測差距是零。

    維持 AoS
    • 一次只處理少量物件，但會用到它幾乎所有欄位
    • 元素會頻繁新增與刪除；陣列結構得同步維護好幾條陣列，交換刪除也要做好幾次
    • 要把單一物件整包傳給別的函式或序列化出去
    • 還沒量過。沒有量測就改布局，是拿可讀性換一個不存在的數字
    改成 SoA
    • 熱迴圈掃過大量元素，卻只讀其中一兩個欄位
    • 打算手寫 SIMD，或希望編譯器願意自動向量化
    • 資料量大到工作集塞不進最後一層快取，被浪費的位元組會直接變成時間
    • 元素數量穩定，生命週期以整批為單位
    折衷做法
    • 冷熱分離：只把熱迴圈用得到的欄位抽成連續陣列，其餘留在原本的結構裡
    • AoSoA：以 8 或 16 筆為一塊，塊內採陣列結構、塊間採結構陣列，同時保住向量載入與局部性
    • 用存取介面把布局包起來，之後要換布局不必動到呼叫端

    布局是前提，不是原因

    三列放在一起，結論就很清楚了：陣列結構本身不會讓程式變快，它只是把向量化的門打開。 門開了卻不走進去，就是第一列的結果；資料量大到快取扛不住時，光是少搬一些位元組也能拿到第二列那種程度的好處； 真正的數倍，要等到一條指令能同時處理八組資料才會出現。 所以決定要不要改布局的問題，其實從來不是「哪一種比較快」，而是「這段程式碼接下來會不會被向量化，以及它是不是真的夠熱」。

    結論

    同樣的工作量，換一種擺法就快得多

    單指令多資料把一個寬暫存器切成多個通道，用一條指令同時完成多份相同的運算，換來的是不需要額外執行緒或核心的平行度。 代價是所有通道必須做同一件事，而這個限制往回傳導到演算法與資料布局：想吃到向量載入的好處，就得讓需要一起算的值在記憶體裡也連續排列，於是有了從結構陣列改寫成陣列結構這種看似彆扭的取捨。 但本頁的實測也說明了另一半的事實——布局只是把門打開，走進去的是向量指令：同樣改成陣列結構，算術密集的重力核心毫無回報，純讀取的加總則實實在在省下被浪費的快取行。 複雜度沒變、工作量沒少，改變的只是硬體被用得多徹底。再往上，還有多核心這一層可以疊加，但要同時吃滿兩層，演算法設計的難度會再上一階。
